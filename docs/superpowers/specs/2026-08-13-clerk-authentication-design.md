# Clerk Authentication Design

**Status:** Approved for implementation planning  
**Date:** 2026-08-13

## Summary

Replace Cloudflare OS's built-in username/password authentication with Clerk while retaining:

- Gatekeeper OAuth sign-in;
- Cloudflare Access authentication; and
- Gatekeepers as post-login service connectors.

Clerk will offer email/password and Google sign-in. In normal deployments the login page will present one unified sign-in card: Clerk first, then retained Gatekeeper sign-in methods below a separator. The Google Gatekeeper sign-in button will be hidden when Clerk Google is offered to avoid duplicate Google choices, but the Google Gatekeeper implementation and connector will remain available.

There are no existing users, so this change requires no account or data migration. New application identities will use stable internal IDs rather than email-keyed User Durable Objects.

## Goals

1. Make Clerk the only email/password implementation.
2. Support Clerk email/password and Google authentication.
3. Preserve Gatekeeper and Cloudflare Access sign-in.
4. Converge Clerk, Gatekeeper, and Cloudflare Access identities when their server-verified emails match.
5. Preserve a user's Cloudflare OS account when their primary Clerk email changes.
6. Keep `ADMINS` as a deployment-controlled verified-email allowlist.
7. Preserve the existing `AuthenticatedApi` capability boundary after authentication.
8. Verify the complete flow locally with Wrangler/workerd before completion.

## Non-goals

- Migrating existing users, passwords, sessions, or email-keyed data.
- Replacing Gatekeepers as service connectors.
- Making Gatekeeper or Cloudflare Access authentication depend on Clerk.
- Automatically merging two already-populated internal accounts.
- Adding Clerk Organizations, Clerk Billing, or role management.
- Moving authentication configuration into the Workshop admin UI.

## Current State

Cloudflare OS currently has three authentication paths:

1. Built-in username/password. The browser derives an Argon2id hash and the backend stores a further SHA-256 digest in the User Durable Object. Successful authentication issues a local random session token.
2. Gatekeeper sign-in. An authentication-capable Gatekeeper completes provider OAuth, supplies a verified email, and the Workshop issues the same kind of local session token.
3. Cloudflare Access. The backend verifies the Access JWT and resolves the User Durable Object directly from its verified email.

User Durable Objects are currently keyed by a username or verified email. Admin access compares that key with `ADMINS`.

## Architecture

### Vendor-neutral identity registry

Add a singleton `IdentityRegistry` Durable Object. It is the sole authority for mapping external identities to stable internal Cloudflare OS users.

It stores these logical indexes and records:

- `(provider, subject) -> internalUserId`
  - initially used for Clerk subjects such as `("clerk", "user_123")`;
- `canonicalVerifiedEmail -> internalUserId`;
- `internalUserId -> { canonicalVerifiedEmail, identityVersion, status }`; and
- active Clerk session subscribers keyed by `internalUserId`, used only to broadcast identity invalidation to live RPC sessions.

`identityVersion` is a monotonic integer incremented whenever canonical email or identity status changes. `status` is `active` or `collisionLocked`.

`internalUserId` is a cryptographically random opaque identifier generated by the registry. User Durable Objects are addressed with `idFromName(internalUserId)`.

Email canonicalization is limited to trimming surrounding whitespace and converting to lowercase. It must not perform provider-specific rewriting such as removing Gmail dots or plus suffixes.

### Identity resolution

All successful authentication paths provide a server-verified identity assertion to the registry:

- Clerk provides a stable Clerk user ID and verified primary email.
- Gatekeepers provide their existing provider-verified email.
- Cloudflare Access provides the verified email from the validated JWT.

The registry resolves authentication atomically:

1. For Clerk, look up the Clerk subject mapping first.
2. If the subject has no mapping, look up the canonical verified email.
3. If the email is already mapped, bind the Clerk subject to that internal user.
4. If neither is mapped, check the Workshop's `signupsEnabled` setting.
5. If signups are disabled, reject account creation.
6. Otherwise generate an internal user ID, establish all mappings, and initialize that User Durable Object idempotently.

Gatekeeper and Access flows resolve by canonical verified email. They reuse an existing internal user when mapped or create one only when signups are enabled.

Concurrent first sign-ins must not create split identities. Identity-registry index resolution and mutation occur atomically within the singleton registry Durable Object's serialized operation. User Durable Object initialization is a separate cross-DO call and therefore is not part of that atomic transaction. It must be idempotent and safely retryable. The authentication flow must not return an `AuthenticatedApi` capability until initialization succeeds. If initialization fails, keep the registry mapping so a retry converges on the same internal user, return an authentication/setup error, and retry initialization on the next authentication attempt.

### Clerk email changes

Clerk's stable subject mapping has priority over email. On each Clerk authentication:

1. Resolve the internal user by Clerk subject.
2. Obtain and validate the current verified primary email.
3. If it differs from the registry's current email, atomically move the email mapping.
4. Remove the old email mapping. The old address must not remain an authentication alias.
5. If the new email is mapped to a different internal user, atomically remove this user's old email mapping, retain the Clerk-subject mapping, set this internal identity to `collisionLocked`, clear its canonical email, increment `identityVersion`, and notify every active Clerk session for this internal user to abort. Do not take or modify the other user's email mapping.
6. While `collisionLocked`, deny all authentication paths and all admin authority for the locked internal user. No new authenticated capability may be minted.

A successful email change also increments `identityVersion` and broadcasts invalidation to every active Clerk session for that internal user, not merely the connection that observed the change. This lets user data follow a Clerk account through non-conflicting email changes without allowing a future owner of the old email to inherit access. A collision leaves no stale email alias and fails closed while preserving enough subject state for a future, separately designed recovery tool.

## Authentication flows

### Clerk

The frontend uses the current `@clerk/react` SDK and initializes `ClerkProvider` with a runtime-provided publishable key. It supports:

- email/password; and
- Google OAuth configured in the Clerk instance.

After sign-in, the frontend obtains a short-lived Clerk session token and invokes a Clerk-specific authentication path. The backend uses the current Clerk backend SDK to verify the token and load the user. It must verify:

- signature;
- issuer;
- expiration and not-before constraints;
- intended audience where configured;
- authorized party/origin using an exact deployment-origin allowlist; and
- a verified primary email obtained from Clerk's trusted backend representation.

The browser must never supply a separately trusted email claim.

The backend then resolves the Clerk identity through the registry and mints the existing `AuthenticatedApi` capability for the resolved internal User Durable Object.

#### Token validation configuration

Production derives the expected Clerk issuer from `CLERK_PUBLISHABLE_KEY` through the Clerk backend SDK. The exact authorized party for a normal production deployment is the origin of `PUBLIC_BASE_URL`; no wildcard is permitted. Local development may additionally allow only the exact origins explicitly listed in `CLERK_DEV_AUTHORIZED_PARTIES` (for example `http://localhost:8787` for `run-local` and `http://localhost:3000` for split Vite development). This development variable is ignored outside local development.

A custom JWT audience is not mandatory for Clerk's standard session token. `CLERK_JWT_AUDIENCE`, when configured, is the single exact expected audience and must be verified. When it is absent, the implementation verifies Clerk's standard issuer plus the required exact `azp`/authorized-party check. Missing `PUBLIC_BASE_URL` or malformed/empty authorized-party configuration is a startup/configuration error in a production Clerk deployment.

### Persistent RPC session

Cloudflare OS uses a persistent Cap'n Web WebSocket. A one-time valid token must not create an indefinitely valid authenticated connection.

The Clerk-authenticated capability therefore has a server-enforced lease whose hard deadline is the verified token's `exp`; it must never extend beyond that claim. The browser may decode `exp` only for scheduling, never for authorization. It requests a fresh Clerk token and refreshes the authenticated RPC lease 15 seconds before expiry (immediately when less than 15 seconds remain). A refresh verifies the new token in full, requires the same Clerk subject and same resolved internal user, reloads the verified primary email, reruns registry resolution, and establishes a new deadline from the new verified `exp`.

Each Clerk-authenticated RPC session registers an abort callback/subscriber with the identity registry for its internal user and unregisters it on disposal. If refresh fails, arrives after the deadline, resolves to another internal user, or detects an identity collision, the backend aborts the entire RPC session and disposes descendant capabilities. If the verified email changed successfully or the identity becomes collision-locked, the registry commits the state/version update and broadcasts invalidation to every registered Clerk session for that internal user. Every such session aborts, including sessions holding previously minted admin descendants. A reconnect succeeds only for an active identity and recalculates all email-derived policy—including admin eligibility—before minting new capabilities.

The registry's subscriber set is in-memory/ephemeral and is re-established by each authentication operation; correctness does not rely on it surviving hibernation or restart. Every Clerk-authenticated session owns one shared revocation guard containing the captured `internalUserId` and `identityVersion`. `AuthenticatedApiImpl` and every authority-bearing `RpcTarget` descendant minted from it—including `AdminApi`, `Overseer`, subscriptions/callback-backed handles, gatekeeper management UI/session capabilities, and future descendants—must be wrapped by or invoke this same guard before each RPC method. The guard asks the registry whether the identity remains active at the captured version; mismatch aborts the entire WebSocket session before dispatching the operation. Capability-returning methods propagate the same guard rather than creating unguarded targets.

This session-wide revocable-capability membrane is the correctness backstop when a broadcast is missed or registry hibernation/restart loses subscribers. Broadcast remains an eager optimization for prompt revocation; the shared guard is authoritative. It is not sufficient to guard only `AuthenticatedApi` and `AdminApi`, because callers can retain and directly invoke child stubs. Cap'n Web session abort/disposal then invalidates all stubs in that WebSocket session.

The browser explicitly disposes/closes its authenticated RPC session immediately on Clerk logout. Server-side/global Clerk logout or revocation is guaranteed to take effect no later than the currently accepted token's `exp`; no webhook-based instantaneous revocation is in scope. The frontend returns to signed-out state after explicit logout, refresh failure, or server abort.

These leases apply only to Clerk-authenticated sessions. Retained Gatekeeper local sessions keep their existing token lifetime/revocation semantics, and Cloudflare Access keeps its existing request/JWT and WebSocket-lifetime semantics. Changing those retained systems is outside this replacement's scope.

The implementation plan must select the smallest Cap'n Web-compatible refresh method/interface that satisfies these fixed behaviors while preserving capability-based authorization and RPC promise pipelining.

### Gatekeeper sign-in

Keep the existing OAuth popup and `PendingLogin` flow. Gatekeepers continue to establish identity using provider-verified email and continue to use local random Workshop session tokens. The token routes to the registry-resolved internal user rather than an email-keyed User Durable Object.

The Google Gatekeeper remains authentication-capable internally, but its login button is hidden when Clerk Google is offered. The Google Gatekeeper remains fully available as a post-login connector.

Other allowlisted authentication Gatekeepers continue appearing below Clerk in the unified sign-in card.

### Cloudflare Access

Preserve Cloudflare Access as a deployment-wide mode. When `CF_ACCESS_AUD` and `CF_ACCESS_ISS` configure Access:

- do not initialize or render Clerk in the frontend;
- preserve Access JWT verification and same-origin checks;
- resolve the verified Access email through the identity registry; and
- preserve `/cdn-cgi/access/logout` behavior.

### Removed password system

Remove the built-in password implementation and its public surfaces:

- password login and signup UI;
- client-side Argon2id password hashing and `hash-wasm` dependency if no longer used;
- password login/signup/change RPC methods;
- stored password digest fields and password-generated local sessions; and
- `DISABLE_PASSWORD_AUTH`, whose distinction is no longer meaningful.

Do not remove local session support still required by Gatekeeper sign-in.

## User initialization, profile, and sharing identity

On first identity creation, initialize the User Durable Object with:

- the stable internal user ID as its storage and application identity;
- the verified email as mutable contact/authentication metadata, not as an identity key; and
- an initial display name derived consistently with the existing verified-email flows.

`AiChatAuthorInfo.id` for a human user becomes the stable internal user ID. Model/agent author IDs retain their existing model-specific semantics. Every durable human reference must use the stable internal ID, including collaborator/share graph entries, chat author records, workspace-owner/collaborator lookup, cached shared-workspace owner profiles, avatar lookup/storage keys, analytics user identity, gatekeeper `userId` context where it denotes the Workshop user, and any profile routes or frontend keys. Human-to-human sharing discovery may accept a verified email as input, but the backend must resolve it through the registry and persist only the resulting internal ID. Presentation surfaces may display the current verified email when explicitly needed, but must not use it as a durable foreign key.

Because there are no users or existing data, changing these identity semantics requires no migration/backfill. Tests must prevent regression to email-based durable references. Later authentication must not overwrite a user-customized display name.

Existing application data—workspaces, gadgets, models, connectors, sharing state, and profile preferences—lives in or references the stable internal user.

## Authorization

`AuthenticatedApi` carries or can access both:

- the stable internal user ID used for application state; and
- the current canonical verified email used for deployment policy.

`ADMINS` remains an environment-provided array of verified email addresses. Admin checks canonicalize configured addresses using the same trim-and-lowercase rule and compare them with the current active registry-verified email captured at authentication/reconnection. `getAdminApi()` checks eligibility when minting; the returned `AdminApi` additionally guards every call against the registry identity version/status captured at mint time. Email/status changes broadcast whole-session invalidation to all active Clerk sessions, while the per-call guard handles missed broadcasts. Reconnection recalculates eligibility using the new email. Deployment changes to `ADMINS` take effect through the existing deployment/restart configuration lifecycle.

Authentication-provider and authorization configuration (`CLERK_*`, `CF_ACCESS_*`, `AUTH_GATEKEEPERS`, and `ADMINS`) remains environment-controlled and must not become writable through `AdminConfig` or an authenticated admin session. The existing Workshop `signupsEnabled` operational policy deliberately remains in `AdminConfig`: admins may open or close first-time Workshop account creation, but cannot alter which identity providers are trusted.

## Frontend UX

### Normal deployments

Use one unified sign-in card:

1. Clerk email/password and Google methods occupy the primary area.
2. A separator introduces retained Gatekeeper sign-in methods.
3. Suppress the Google Gatekeeper login button while Clerk Google is configured.
4. Keep connector setup out of the sign-in UI.

The frontend relies on Clerk for Clerk-session persistence and logout. It must not save Clerk tokens in `localStorage`.

### Error handling

Present bounded, actionable errors for:

- Clerk loading or configuration failure;
- invalid or expired sessions;
- disabled Workshop signups after successful Clerk authentication;
- missing/unverified primary email;
- identity collision requiring operator assistance; and
- unavailable Gatekeeper sign-in.

Do not expose token contents, provider payloads, internal Durable Object IDs, or Clerk profiles in browser errors. Collision recovery is deliberately unavailable and out of scope for this change: the registry preserves the Clerk subject mapping in `collisionLocked` state, removes the stale email alias, denies authentication, logs a bounded collision event, and instructs the user to contact the deployment operator. Do not add an admin merge UI, automatic merge, or identity-remapping RPC. Any future recovery tool requires a separate security design.

## Observability and privacy

Backend authentication logs use the existing structured logger. They may record:

- authentication provider;
- operation and stable event name;
- bounded outcome code;
- whether account creation occurred; and
- internal correlation fields already allowed by project policy.

Never log passwords, Clerk secret keys, publishable tokens, session tokens, JWTs, OAuth payloads, prompts, headers, or complete Clerk user profiles. External issue reports follow the same data-minimization rules.

## Configuration and deployment

### Clerk application

Use the Clerk CLI to create and link a new application. Configure:

- email/password authentication; and
- Google authentication.

Run `clerk doctor --json` before other Clerk operations. Preview every Clerk configuration mutation before applying it. Pull development credentials only into gitignored local environment files.

### Runtime configuration

Required values:

- `CLERK_PUBLISHABLE_KEY`: public, delivered to the frontend through runtime `ServerConfig` rather than compiled into release assets;
- `CLERK_SECRET_KEY`: Worker secret used for Clerk Backend API calls; and
- optionally `CLERK_JWT_KEY`: deployment secret/configuration for networkless JWT verification when supported by the chosen SDK setup;
- `CLERK_JWT_AUDIENCE`: optional single exact audience for a custom Clerk JWT configuration; and
- `CLERK_DEV_AUTHORIZED_PARTIES`: local-development-only list of exact frontend origins.

`PUBLIC_BASE_URL` supplies the sole production authorized origin. `CLERK_SECRET_KEY`, `CLERK_JWT_KEY`, and any other private material are Worker secrets. `CLERK_PUBLISHABLE_KEY`, `CLERK_JWT_AUDIENCE`, and exact authorized origins are non-secret deployment configuration.

The release pipeline builds frontend assets once for multiple customer installations. Therefore no customer-specific publishable key or secret may be embedded in the frontend bundle.

### Release pipeline

Update:

- Worker environment types;
- deployment manifest inputs/placeholders;
- deploy-wizard configuration;
- release manifest golden files;
- local `.dev.vars` loading/pass-through; and
- deployment documentation.

Normal non-Access deployments require valid Clerk configuration. Missing Clerk configuration must produce a clear deployment/startup configuration error rather than silently restoring built-in password login.

Cloudflare Access deployments remain valid without initializing frontend Clerk.

## Security invariants

1. Every accepted email originates from a server-verified identity assertion.
2. Clerk subject is the stable Clerk identity; email is the cross-provider convergence key.
3. Old email mappings are removed after a verified Clerk email change.
4. Populated identities are never automatically merged; collision atomically removes the stale alias, locks the affected identity, preserves its Clerk subject mapping, and invalidates all sessions.
5. Signup policy is checked at the backend trust boundary before first internal-user creation.
6. Clerk tokens are bounded by the issuer derived from the publishable key, an optional exact configured audience, an exact authorized party derived from production `PUBLIC_BASE_URL` (or explicit local-only origins), and verified lifetime claims.
7. A Clerk-authenticated WebSocket cannot outlive the accepted token's `exp`; refresh re-verifies identity, and email change aborts the session before policy is recalculated.
8. Admin authority derives only from deployment-controlled `ADMINS` and an active current verified email; registry broadcasts plus a shared per-session revocation guard on every descendant capability revoke stale authority across concurrent sessions.
9. Authentication secrets and identity payloads are never logged or embedded in release artifacts.
10. Retained Gatekeeper and Access flows do not become dependent on Clerk availability.

## Testing and acceptance criteria

### Unit and integration tests

Backend coverage must include:

- valid Clerk token authentication;
- invalid signature, issuer, audience/authorized party, expiration, and not-before rejection;
- missing or unverified primary-email rejection;
- first-user creation;
- disabled-signup rejection for an unknown identity;
- existing-user sign-in while signups are disabled;
- Clerk email change with old mapping removal;
- Clerk/Gatekeeper/Access convergence by canonical verified email;
- collision when a changed Clerk email belongs to another user: stale alias removed, subject retained, identity collision-locked, other mapping untouched, all authentication/admin access denied;
- concurrent first sign-ins resolving to one internal user;
- idempotent User Durable Object initialization;
- stable internal IDs in `AiChatAuthorInfo.id`, sharing/collaborator references, avatar keys, cached owner profiles, blueprint ownership, presence, output indexes, profile routes, and Gatekeeper Workshop-user context, with email accepted only as registry-resolved discovery/contact input;
- admin matching with canonical verified email;
- non-admin denial;
- WebSocket hard expiration at token `exp`, proactive refresh, refresh after expiry, subject/internal-user mismatch, explicit logout, and failed refresh;
- cross-session abort and admin-capability denial after a verified Clerk email change, including two simultaneously active sessions where one holds an `AdminApi` capability;
- missed-broadcast/registry-restart simulation proving the shared revocation guard denies direct calls through stale `AuthenticatedApi`, `AdminApi`, an already-minted `Overseer`, and another representative child capability, then aborts the whole WebSocket session;
- capability propagation tests proving every authority-bearing descendant receives the same session guard;
- retained Gatekeeper token authentication; and
- retained Cloudflare Access authentication/logout.

Frontend coverage must include:

- unified Clerk/Gatekeeper card;
- email/password and Google Clerk options;
- Google Gatekeeper button suppression;
- retained non-Google Gatekeeper buttons;
- Clerk loading, signed-out, signed-in, and error states;
- refresh scheduling 15 seconds before token expiry, refresh failure, server abort, and logout;
- no Clerk token persistence in `localStorage`; and
- Cloudflare Access mode not initializing Clerk.

Release coverage must include:

- Clerk deployment inputs and placeholders;
- manifest golden-file changes;
- absence of Clerk secrets and customer-specific keys in built frontend assets; and
- clear missing-configuration failure.

### Required local end-to-end verification

Before completion, run the whole stack locally with Wrangler/workerd and the Clerk development instance. Verify in a real browser:

1. Create a new account with Clerk email/password and reach an authenticated workspace.
2. Sign out and sign back in with the same Clerk credentials.
3. Sign in with Clerk Google.
4. Confirm the Google Gatekeeper sign-in button is hidden while the Google connector remains available after login.
5. Sign in through a retained non-Google Gatekeeper and confirm email convergence reaches the same internal account where applicable.
6. Exercise the Cloudflare Access path through automated/local integration coverage or an Access-capable test environment if local Access emulation cannot issue a valid Access assertion; document that limitation explicitly.
7. Disable Workshop signups and confirm a new Clerk identity is rejected while an existing identity still signs in.
8. Change the Clerk primary email and confirm the same workspaces remain accessible and the old email no longer authenticates that account.
9. Confirm Clerk logout removes access and a stale/expired token cannot continue using the authenticated WebSocket after its lease.
10. Inspect built frontend assets to confirm no Clerk secret key or customer-specific runtime key was embedded.

The implementation is not complete until relevant `pnpm test`, `pnpm lint`, package builds/type checks, and the local end-to-end checks pass, with any environment-limited check called out explicitly.
